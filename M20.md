# M20 fork of the Fixposition ROS driver

This fork adds the localization interface that the **Deep Robotics M20** quadruped's navigation
stack expects, so that one process does what previously took the driver plus two Python bridge nodes
on the robot's host.

Upstream behaviour is untouched: everything below is off unless `m20.enable` is set.

Branch `m20` is based on upstream `3f75c62` (8.0.2-11), the commit the deployed container image is
built from — deliberately not upstream `main`, to keep a Fixposition SDK bump out of the same change.

## What it adds

| Package | Role |
|---|---|
| `drdds` | Wire-compatible subset of the robot's own interface package, vendored so the container can speak to it. See [drdds/README.md](drdds/README.md) — it explains why the package name and field layout are load-bearing. |
| `fixposition_driver_m20` | The localization module itself: the three OEM topics, the deskewing numerics, and the health state machine. |
| `fixposition_driver_ros2` | ~40 lines of hooks: create the module, feed it the ENU fusion output, forward wheelspeed, re-exec on the self-heal request. |

## The interface

Three topics that **share one timestamp**, with `/ODOM` leading:

| Topic | Type | Rate | QoS | Notes |
|---|---|---|---|---|
| `/ODOM` | `nav_msgs/Odometry` | 10 Hz | reliable, depth 10 | frame `map`, **empty** child frame, zero covariance — matching the OEM's own output. Published straight from the sensor's `FP_A-ODOMENU`, in the parser thread, so nothing downstream can delay it. |
| `/LOC_BODY_POINTS` | `sensor_msgs/PointCloud2` | ~10 Hz | best effort, depth 5 | the lidar scan motion-compensated into `base_link` at the newest `/ODOM` stamp |
| `/LOCATION_STATUS` | `drdds/LocationStatus` | 2 Hz | reliable, depth 10 | `total_status` 0 uninitialized / 1 normal / 2 low quality / 3 lost |

Inputs: `/LIDAR/POINTS`, `/IMU`, and `/MOTION_INFO` (`drdds/MotionInfo`), whose body velocity is
forwarded to the sensor as wheelspeed aiding — replacing the `converter` + external Twist bridge.

## Design notes

**Why the stamps are shared.** The navigation stack correlates the three topics by timestamp. `/ODOM`
is published the instant the fusion output is parsed and carries its own stamp; the deskew worker
then stamps the cloud and the status with the *newest* `/ODOM` stamp, so their stamp is always that
of a real odometry message. A scan that arrives while the worker is busy replaces the pending one
(latest scan wins) — a stale cloud helps nobody, and dropping it keeps the odometry unaffected.

The shared stamp is the normal case, not a guarantee. Until the first odometry message there is no
reference, and the cloud keeps the scan's own stamp. When the newest odometry stamp is more than
`m20.timestamp_skew_threshold_sec` away from the scan — the clocks disagree, or the odometry has
stopped — the cloud again keeps the scan's stamp, is deskewed without the translation term, and the
status flags a timestamp error.

**Odometry source.** `m20.odom_source` names the one feed the module follows. There is no fallback
from one feed to the other.

| Mode | The sensor's ENU output (`FP_A-ODOMENU`) | Another node's `/ODOM` |
|---|---|---|
| `fpa_odomenu` | published as `/ODOM` and on the handler alias (`m20.handler_odom_topic`); stamps the cloud and the status; keeps the status alive | not subscribed |
| `subscribe` | marks the RTK input as arriving, and nothing else: not published, not a stamp or velocity reference, does not initialize the status or keep its odometry alive | republished on the handler alias; stamps the cloud and the status; keeps the status alive |

So in `subscribe` mode a SLAM pipeline that stops publishing is reported as lost (`total_status` 3,
`loss_val.odom_error` 1) even while the sensor still has a valid ENU pose, and the status stays
uninitialized until the pipeline's first `/ODOM`. `input_val.rtk` in that mode means "the pipeline's
`/ODOM` or the sensor's ENU output is arriving". It says nothing about GNSS health, and it stays set
indoors for as long as the pipeline publishes.

**Deskewing.** Each point is rewritten as `p_ref = R(ref <- i) * p_i + v_body * (t_i - t_ref)`, with
`R` from integrated IMU body rates and `v_body` from the newest odometry. Rotations are evaluated once
per 1 ms bucket rather than per point: 1 ms at 2 rad/s is ~0.1°, far below lidar noise, and it turns
thousands of Rodrigues evaluations into about a hundred. The transform runs in place on the message's
own buffer, and the message is then moved into the publisher — no copy of the ~1 MB cloud at any point.

**Clock retiming.** `m20.retime_to_host_clock` slides the sensor's stamps onto the host clock using a
median of `(host now − sensor stamp)`. With the robot's PTP chain healthy this is a no-op; it earns
its keep when GNSS time is lost and the sensor's clock drifts away from the lidar's.

**Startup self-heal.** A DDS participant created at boot has twice been observed coming up deaf to
same-host publishers — no lidar, no IMU, no leg odometry, indefinitely. If nothing at all arrives
within `m20.boot_reinit_grace_sec`, the process re-executes itself (same PID, fresh participant), up
to `m20.boot_reinit_max` times, then gives up and keeps reporting the failure honestly in the status.

**Cross-distribution DDS.** The robot runs Foxy; this driver runs in a Humble container. Verified by
serializing fixed messages on both sides and comparing bytes: the CDR payloads are identical, and the
type names match by construction. Humble's serializer appends up to 3 bytes of trailing alignment
padding on odd-sized messages (`LocationStatus`: 36 bytes vs Foxy's 34), which readers ignore.

## Configuration

See [`fixposition_driver_ros2/launch/config_m20.yaml`](fixposition_driver_ros2/launch/config_m20.yaml)
for a complete, commented example. The minimum is:

```yaml
m20:
    enable: true
    odom_source: "fpa_odomenu"   # "subscribe" when a SLAM pipeline publishes /ODOM instead
```

## Tests

The numerics, the health state machine and the odometry source policy are ROS-free and covered by
gtest:

```bash
colcon build --packages-select drdds fixposition_driver_m20
colcon test --packages-select fixposition_driver_m20 && colcon test-result --all
```

## Merging upstream

The hooks in `fixposition_driver_ros2` are small and localized (constructor, `StartNode`, the
`FP_A-ODOMENU` observer, `StopNode`, `main`). Everything else lives in packages upstream does not
have, so pulling a new upstream tag should be a matter of re-applying those hooks.
